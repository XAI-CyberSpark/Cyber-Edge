# Hermes 编排增加多角色分工层

日期：2026-09-27（dev.68）。状态：用户确认；已实现，未提交、未发布。依据：docs/product/releases/2.8.0-dev.68/PRD.md。

## 决策

沿用固定修订的官方 Hermes SDK（hermes_authoring.py 中 SDK_COMMIT），在原单 Agent 编排之上增加 team 模式：主管加需求员、状态/路径设计员、节点搭建员、测试员四个专业角色。各角色使用同一配置模型，但各自是独立 AIAgent 上下文。

- 专业角色只读真实节点能力，通过各自的 oakegde_deliver_<role> 工具提交版本化、结构化成果；只有主管能按成果 ID 应用、驱动图事务和试跑（authoring_team.py）。
- 委派有依赖顺序：需求先于其余角色，搭建需要已有设计成果，测试需要图中已有节点。首版串行，不声称并行调度，也不启用 SDK 的 delegate_task。
- 最终验收不变：现有图执行器、锁定输入/断言、三次执行、独立上下文的内容核验员。分工本身不作为质量证明。
- 单/多模式共用 40 次编排 completion 尝试与 720 秒编排期限，宿主 780 秒取消整组进程；预算覆盖主管和子 Agent。
- 没有真实接口的动作可以进入设计，但必须标注缺失，不能用文字代替实际动作宣称成功。

## 模式选择

API 字段 agent_mode 可为 single/team，省略时使用服务端配置。注意两层默认值不同：代码 EngineConfig 缺省为 single；当前 .demo-runtime/orchestration-engine.json 配置为 team。“服务端默认 team”指当前部署配置，不是代码缺省。

## 影响

- 保留原 UI 流程与 HMI，只改变后端编排机制。
- 对照评测必须固定需求、模型、代码版本和预算；不同模型或代码的结果不合并为同一基准。
- 已满足全部角色和同版本严格验收的结果可由宿主调用原提交逻辑收尾，报告须标明宿主来源。
- 实际对照结果与未通过项见 dev.68 ACCEPTANCE，本 ADR 不记录通过率。

## dev.95交付语义检查补充（2026-10-06）

需求员交付先调用会话的只读validate_brief，语义拒绝反馈给同一子Agent修正；有效交付不等于已登记，仍由主管apply。角色上下文补齐带role的讨论，用户原话来源/验收锁不放宽。主依据：[dev.95验收](../product/releases/2.8.0-dev.95/ACCEPTANCE.md)。


dev.102（2026-10-08）用户明确授权：共享编排预算由24次/480秒放宽到40次/720秒，宿主540→780秒。此前版本数字仅为历史证据；当前期限审计、真实结果及限制见[本轮验收](../product/releases/2.8.0-dev.102/ACCEPTANCE.md)。图执行与独立内容核验的局部预算保持。


预算收尾沿用完整trial及独立内容核验；核验不可用沿用原重试、失败保持incomplete_result。host_finalized只标记宿主来源，不能代替can_apply；执行/核验调用另计。仅剩余宿主时间≥245秒时可启动，低于此值报告跳过。无有效计划不自造测试。


dev.103（2026-10-08）：每次编排API请求单独默认150秒，来自EngineConfig.api_call_timeout_seconds，由worker profile同时配置custom/anthropic；取代dev.102单请求720秒。整轮40次/720秒、宿主780秒保持。正常SDK重试计入编排次数，超时快照回传最后revision及计数，不改变本ADR架构。
