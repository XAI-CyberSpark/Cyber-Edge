# OAKEgde Studio 设计规范

状态：现有约定汇总，不代表所有界面已验收｜维护日期：2026-09-25｜适用范围：Web 工作台与 HMI

[返回项目主文档](../README.md)

目的：把分散在上下文、技能约定和版本记录中的现行设计选择集中管理，避免每次修改重新解释产品。本规范随用户已确认的界面修改维护；各轮实施范围见迭代记录。具体行为与验证范围以所链接的迭代记录为准。

## 1. 界面职责

| 区域 | 用户在这里做什么 | 应保持的边界 |
| --- | --- | --- |
| 场景共创聊天 | 描述、修改和生成体验方案，选择创作模型 | 简洁聊天；详细配置按需展开，避免把执行调试项堆进对话 |
| 场景测试聊天 | 输入文字、上传图片、观察当前流程回应 | 保留聊天记录、底部输入、一个附件按钮和发送；视频来源等在节点配置处理 |
| 节点画布与详情 | 看流程，查看或配置能力 | 业务名称清楚，技术细节按需展开；新的分层画布仍是节点定义草案 |
| HMI | 呈现座舱用户实际看到的效果与动作反馈 | 模拟与真实来源准确，不能靠动画暗示动作已完成 |
| 组件库/项目/记录等导航面板 | 按需查找与管理资源 | 保持统一外壳；打开关闭保留底层画布与仿真状态 |

HMI 助手与右侧聊天是不同入口：HMI 助手当前以麦克风输入需求；右侧场景测试继续允许文字与图片。不要把其中一个入口的输入约定套到另一个上。

依据：[dev.25 任务与需求](<releases/2.8.0-dev.25/TASKS.md)、[dev.26 任务与需求](releases/2.8.0-dev.26/TASKS.md)、[dev.33 需求](releases/2.8.0-dev.33/PRD.md>)。

## 2. 视觉与资产约定

- HMI 保留纯黑、灰白与少量状态色、既有车模和主要布局；首页保留已确认的 Prism、玻璃项目卡片、Logo、像素标题和 Shuffle。两种界面风格按范围适用，不将 HMI 的黑色规则扩散到所有页面。
- 字体按用户2026-09-25最新决定：通用UI/HMI采用系统无衬线（苹方/微软雅黑等回退），代码与日志采用普通系统等宽；首页Press Start 2P像素标题及动效保持。此项替代dev.17全局Maple，详见[dev.38验收](releases/2.8.0-dev.38/ACCEPTANCE.md)。参考截图字体无法仅凭图片确切识别，不声称已安装其专有字体。
- Bloub 保留原版轮廓、眼睛与动画节奏；状态来自实际待机/思考/提醒，不自动轮播展示。
- Figma 参考按用户指定节点和范围实施，不能自动同步整个文件。顶部、Dock 与助手是不同迭代；[技能约定](APPLE_DESIGN_SKILLS.md)中的最初顶部/Dock 范围不撤销后续明确授权的助手修改。
- AppIcon 动效响应真实状态，保留既定 Figma 图片图标及角色资产；减少动态效果时提供直接切换，不用动画代替能力完成。

依据：[Apple 设计技能约定](<APPLE_DESIGN_SKILLS.md)、[dev.17 记录](releases/2.8.0-dev.17/ACCEPTANCE.md)、[dev.28 记录](releases/2.8.0-dev.28/ACCEPTANCE.md>)。设计技能只是实施参考；用户最新指定内容与项目约定优先。

## 4. 产品表达与状态反馈

- 主操作简短明确；接入信息、参数、日志和诊断放在需要它们的位置，避免用大量常驻文字让用户理解内部实现。
- “正在识别”“正在播放”“已执行”等词必须对应真实状态；模型失败、视频不可用、取消后的迟到结果分别处理。
- 演示录像注明演示，不标为实时；关闭提醒不代表风险解除。模型自评分不是准确率。
- 创作草案、可执行能力和实际执行结果分别呈现，避免用户把故事里的动作当成设备已经执行。
- 控件不可用时说明具体缺少的条件；不添加未接入的功能入口假装可用。详细失败证据可查看，主要反馈保持简短。

## 5. 修改后的检查

在本次范围内检查真实页面、目标宽度和窄面板：可读、无意外横向溢出、长内容处理、键盘焦点、关闭恢复和减少动态效果。异步界面还要检查加载、失败、取消与迟到结果；需要播放或设备回执的功能核对实际状态。

将检查环境、使用真实服务还是模拟数据、截图/结果与未验证项写入当轮 ACCEPTANCE。旧截图不是新变更的通过证明。

## 7. 后续 AI 前端修改规则（dev.42）

目的：减少局部需求触发无关的视觉变化；具体值与例外见[参数与组件基线](DESIGN_TOKENS.md)。

1. 开始前读本规范及参数基线中受影响的部分，确认目标是首页、工作台、导航、共创聊天或HMI。读取实际组件、CSS导入顺序与后段覆盖；禁止把历史outputs副本当作当前实现。
2. 在执行说明中明确本轮改变的区域/行为。改文字沿用已有排版，改一个组件沿用周边布局；用户明确要求重设计时按指定范围调整，不把这条规则变成额外审批要求。
3. 复用已有语义色、公共组件、模块局部变量和资产。优先调整现有variant或作用域内规则，不随意新增近似HEX、平行按钮实现、全局CSS覆盖或 `!important` 链。
4. 全局主题、系统字体、页面骨架、面板宽度、首页资产、HMI车模/Bloub的变化必须直接服务于本轮明确目标。局部“更美观/更整齐”不足以推翻已确认选择。
5. 样式冲突区分“已确认约定”“当前源码”“待决定”。不要把旧声明、未调用组件或未验证断点写成最终验收事实；仅在会影响本轮结果时澄清必要取舍。
6. 视觉变更在真实页面对照修改前后状态，检查目标尺寸、受影响容器、交互状态与键盘焦点；保留基础状态不因面板开关而丢失。文档提取仅做参数与链接检查，不假报页面测试。
7. 收尾记录改了什么、检查了什么、仍未确认什么。同步本规范/参数基线的受影响条目和迭代验收；不重复创建第二套设计主文档。
