# OAKEgde Studio 产品开发流程

版本：0.1｜状态：流程基线，供后续迭代使用｜日期：2026-09-11

## 从这里开始

每次只推进一个可以验收的小版本。先确认用户要完成的任务，再设计方案；先打通一个完整场景，再扩展能力。个人开发时可以由同一个人承担产品、研发和测试角色，但仍需要分别检查需求、实现和结果。

当前阶段：已有工程原型，正在补齐产品定义与验证依据。已有功能不自动等于已验收功能。以下流程不代表产品范围和商业假设已经确认。

## 一次迭代的八个步骤

| 步骤 | 你需要做什么 | 最小产物 | 进入下一步的条件 |
|---|---|---|---|
| 1. 发现问题 | 访谈或观察目标用户，记录当前如何完成任务 | 用户、问题、现有方式、证据 | 能用一个具体例子说明问题；假设与事实分开 |
| 2. 确定范围 | 选一个最重要的任务，说明本版做什么 | PRD 中的目标、范围、非目标 | 用户、交付终点、优先级明确 |
| 3. 定义场景 | 写正常路径、异常路径和验收条件 | 场景规格、用例 | 每个核心需求都有可检查的预期 |
| 4. 设计方案 | 画主要页面与操作流程，明确数据和接口 | 原型、必要的技术方案或 ADR | 用户能完成任务；依赖与技术疑点有处理方案 |
| 5. 拆分开发 | 把需求拆成小任务，标注依赖 | 任务清单 | 每项任务有输出和完成条件 |
| 6. 实现与自测 | 逐项开发，保持需求与实现同步 | 代码、针对性检查记录 | 核心用例通过；没有未说明的阻塞 |
| 7. 验收与发布 | 按用例检查目标环境，保留证据 | 验收报告、版本说明、回滚方法 | 失败项与限制明确；交付物可复现 |
| 8. 试用与复盘 | 让目标用户实际使用，记录结果 | 反馈、指标、下一轮优先级 | 下一轮改动有证据支持 |

## 文档如何保持轻量

每个版本建立 `docs/product/releases/<版本号>/`，使用三个文件：

- `PRD.md`：问题、范围、需求、场景、验收预期。
- `TASKS.md`：任务、状态、依赖、实现位置和检查结果。
- `ACCEPTANCE.md`：环境、版本、用例结果、证据、限制和发布结论。

小修改可以直接在任务中写清需求与验收，不必复制完整 PRD。改变产品范围、接口契约或运行方式时，再补对应设计文档与 ADR。开始新版本前先复制模板，未确定内容写“待确认”，不要填成已完成。

## OAKEgde Studio 的特别规则

1. **交付终点必须明确**：本版交付可运行原型、验证报告、还是目标设备运行包？三者分别验收。
2. **区分运行模式**：模拟输入、真实模型、真实设备分别记录。模拟用例通过不能证明模型准确率或设备性能。
3. **场景规格是共同依据**：描述触发、环境、状态、动作、反馈、异常和验收；工作流与仿真都需要对应这些定义。
4. **修改使旧结果失效**：规格、工作流或关键模型配置变更后，重新执行受影响用例。记录版本之间的对应关系。
5. **明确能力来源**：节点依赖的模型、接口、设备与不可用时行为要写清。界面显示“成功”不能代替实际动作反馈。
6. **用第二个场景检验复用**：平台扩展前，确认新场景能复用已有规格和环境机制；新增专用代码要记录原因。

## 需求与结果的追踪方式

使用简单编号即可，例如：`REQ-001 → SCN-001 → TASK-001 → TC-001`。

| 需求 | 场景 | 开发任务 | 验收用例 | 状态与证据 |
|---|---|---|---|---|
| REQ-001 后排风险提醒 | SCN-001 儿童探窗 | TASK-001 告警流程 | TC-001 首次风险 | 待执行，不预填通过 |

只有实现、相关检查和文档都完成，任务才标记完成。未完成项进入待办，不藏在“基本完成”里。

## 如何与 AI 共创

你提供真实用户背景、优先级和产品取舍；AI 协助梳理问题、检查代码、设计方案、实现和验证。没有证据时，AI 应明确标注假设。

可直接使用的协作指令：

> 本轮目标是……，用户是……，当前最痛的问题是……。先帮我补齐这一轮的 PRD 和验收条件，指出待确认项；范围明确后拆任务，再按任务实现并记录验证结果。
