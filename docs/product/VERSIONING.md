# OAKEgde Studio 版本管理规则

生效日期：2026-09-11。

## 当前版本与唯一入口

根目录 VERSION 是产品版本的登记入口，具体编号见 [VERSION](../../VERSION)，这里不重复手写当前值。`2.8.0-dev.1` 是接管版本管理后的第一个开发编号，不表示历史已经发布过 2.8.0，也不表示当前代码通过验收。

Studio 与 Desktop 的包版本均为 2.8.0；Python API 元数据为 1.0.0；Rust core 为 2.0.0。本轮不修改这些组件元数据。产品版本与组件版本分别记录；正式打包时需要记录实际使用的组件版本和代码提交。

## 编号规则

- `2.8.0-dev.1`、`2.8.0-dev.2`：面向目标 2.8.0 的开发迭代。完成一轮范围明确的开发迭代后，下一轮增加 dev 编号。
- `2.8.0-rc.1`：功能范围冻结后的候选版本，用于完整验收；发现问题后修正并生成新的 rc 编号。
- `2.8.0`：验收通过、发布材料齐备的正式版本。
- 正式版之后，兼容性修复使用 `2.8.1`；兼容的新功能使用 `2.9.0`；破坏已承诺的兼容性时考虑 `3.0.0`，并说明迁移方案。

一次对话、一个文件修改、一次 Git 提交不自动成为新产品版本。用户确认的新一轮功能范围或清晰独立的交付目标，才建立新迭代编号。当前轮次的补充、修复和验收继续归入同一轮。

## 每轮必做

1. 开始前读取 VERSION、CHANGELOG.md 和当前版本目录。
2. 新迭代记录目标、范围、非目标、前置依赖和验收条件。范围未定时明确写待确认。
3. 实现期间维护任务状态，将改动关联需求和验收用例。
4. 结束时记录实际完成、未完成、验证结果和已知问题；更新变更日志。
5. 未测试、模拟测试和真实环境测试分别记录，失败时不升级为正式版。
6. 修改版本号时同步根 VERSION、变更日志和文档导航中的当前状态。

版本目录：`docs/product/releases/<产品版本>/`，使用 PRD.md、TASKS.md、ACCEPTANCE.md。初始接管版本允许使用 BASELINE.md 汇总历史现状；新增产品需求从下一轮或补齐当前轮 PRD 开始。

## Git 与可恢复版本

版本号只是登记，Git 提交与标签才用于准确定位代码。工作区存在未提交改动时，必须注明“未提交工作区”，不能把 HEAD 当成完整当前版本。

准备开发快照时先检查差异、敏感配置和用户尚未完成的工作，只提交范围明确的文件。不得用 git add . 混入未知工具、密钥或无关工作。未获得适用的提交授权时，不自动提交。2026-10-03 用户授权整理 Git 基线，当前恢复入口见 [dev.78 基线](releases/2.8.0-dev.78/BASELINE.md)；历史接管阶段未提交的记录不自动代表当前状态。

正式发布应有：明确的代码提交、对应版本记录、验收报告、交付物、安装与恢复说明。满足条件后创建不可随意移动的 `v2.8.0` 等标签，记录产物校验值。不要给脏工作区的 HEAD 打标签并声称包含全部改动。

历史不补造：已有 baseline-20260713 保留原样；没有证据的过往迭代登记为未编号历史，不虚构版本、日期或验收结果。

## 项目管理职责

AI 在本仓库工作时维护版本、范围、任务、验收与遗留问题，结束时报告当前编号和状态。用户决定业务目标和优先级；AI 可直接登记明确的迭代变化，不必为日常编号维护反复询问。

该规则在后续任务读取仓库时执行；不代表后台持续监控或自动定时发布。

## 开发记录与产品更新分工（2026-10-05用户确认）

- 内部开发记录保留在根CHANGELOG及版本目录；小修正、同一功能的补充与验收继续使用原编号。编号不是正式发布次数，也不保证存在可恢复快照。
- 面向读者的[产品更新](../developer/UPDATES.md)按周汇总，完整功能验收后可补充。同一周持续编辑同一汇总，不因每条开发编号新增一条公告；无显著变化可不新增汇总。该规则在协作任务中执行，不代表后台定时任务。
- 汇总按“日期与主题 → 状态 → 条目”组织。每条使用“新增/改进/修复/待验收 + 功能名称 + 用户可理解的变化”，必要时注明验证边界，禁止拼成长段或截断开发日志。底部关联开发记录，避免复制验收全文。
- 正式发布记录仅在实际验收、产物及发布证据齐备后建立，不能把周报或本机更新称作正式发布。历史开发编号原样保留，不重编号。
