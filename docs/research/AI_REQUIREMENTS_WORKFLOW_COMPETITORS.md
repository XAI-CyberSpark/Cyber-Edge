# AI 需求定义与工作流编排竞品调研：Coze、Dify、Kiro

归档位置：项目主文档 → 竞品调研；[飞书在线阅读](https://bi98l1v0z9.feishu.cn/docx/LJR9dexgPoj0WXx9YvLcitQdnEd)。

目的：归纳三家如何用 AI 理解需求、形成实现和验证结果，为 OAKEgde Studio 的场景编排提供参考。本报告不直接修改既有产品规范；其中建议需进入明确的后续迭代才能视为实施承诺。

## 核心结论

OAKEgde Studio 可以借鉴 Kiro 的需求规格与持续上下文、Coze 的自然语言创作和局部修改、Dify 的执行编排与可观测性，把理解需求、创作体验、落实能力、验证结果连成完整过程。

节点契约固定能力边界，体验方案保留创作空间。可靠性要分别证明需求理解、结构合法、运行行为、模型任务效果和最终体验，不能合并成一个“生成成功”。

本报告基于官方公开资料，能确认产品描述了哪些机制；不能证明三家在儿童关怀、生日航海或任意场景上的成功率，也不能推断其未公开提示词、模型训练方法和内部编排算法。

## 研究问题与方法

本次回答三个问题：AI 怎样把自然语言变成需求或流程；产品采用哪些检查与修复机制；OAKEgde Studio 应借鉴哪些做法、保留哪些不同的领域要求。

方法：整理本次对话中于2026-09-25查阅的官方文档与官方产品说明，按“需求输入—中间产物—实现—验证—持续修改”对照。不采用第三方营销测评作为产品能力证据，不涉及用户访谈、付费账户实测或代码审计；这是一份探索性的公开资料调研，不是系统性市场排名。

对象范围：Coze 主要研究中国版扣子编程的生成式工作流，不能与所有传统节点编辑器混为一谈；Dify 区分 Workflow Studio 与官方2026-08-27介绍的新版 Agent Build Mode；Kiro 研究规格驱动开发，它本身不是同类座舱节点执行平台。具体入口与可用性还会受版本、部署形态和账户权限影响。

## 三家做法对照

| 对象 | 怎样定义需求 | 形成什么产物 | 检查与迭代方式 | 本次不能据此证明什么 |
| --- | --- | --- | --- | --- |
| Coze / 扣子编程 | 自然语言描述，附件补充；不清楚时先问答讨论 | 工作流代码、可视化节点及参数 | 自动测试、全链路试运行、节点解释与定向修改 | 任意需求一次生成正确；所有接口都可自动接入 |
| Dify | 画布明确流程；新版 Agent 通过对话、试做、纠正形成配置 | 工作流、Agent 指令、技能与工具配置 | 节点调试、运行轨迹、失败路径和人工介入 | Build Mode 等于任意完整工作流自动生成；生产环境必然可靠 |
| Kiro | 将愿望整理成用户故事、验收条件、设计和任务 | requirements.md、design.md、tasks.md | 需求分析、逐步审阅或 Quick Spec，后续同步修改 | 规格文本自动等于正确实现；已具备座舱设备运行能力 |

对照依据：[扣子工作流开发](<https://docs.coze.cn/guides_ai_powered_workflow_development)、[Dify Workflow Studio](<https://dify.ai/workflows)、[Dify 新版 Agent](https://dify.ai/blog/why-we-redesigned-dify-agent>)、[Kiro Requirements-First](https://kiro.dev/docs/specs/feature-specs/requirements-first/>)。以下进一步区分公开做法和我们的分析。

## Coze：通过业务描述生成和修改工作流

官方公开的生成式工作流支持自然语言生成代码、按需使用技能与集成、自动测试及试运行。画布节点可查看参数，也可选中后让 AI 解释或修改。其文档描述语义、参数、代码三个层次，并允许独立功能或组合功能成为执行节点。[官方工作流文档](https://docs.coze.cn/guides_ai_powered_workflow_development)

需求不明确时可先用问答模式讨论，再由 Agent 执行。另有计划模式，但相关说明限定于网页、移动应用和小程序，不能据此称工作流也支持同样的计划入口。[官方协作模式说明](https://docs.coze.cn/guides_vibe_coding_faq)

我们的分析：用户可以先表达目标和修改意图，再由系统处理实现细节。OAKEgde Studio 应允许“在这里加一个惊喜”这样的业务操作，同时保留参数与执行依据供排查。

限制：生成代码仍可能不符合预期，官方提供修复和回滚机制。生成出的新节点需要真实实现与运行依据；画布上出现一个节点不能证明外部能力已经接通。[官方修复与回滚说明](https://docs.coze.cn/guides_ai_powered_workflow_development)

## Dify：灵活完成任务，明确组织执行

Workflow Studio 提供节点与变量连接、单步/整流调试、失败路径、运行记录和版本管理。这些机制让开发者能观察一次执行经过哪里、输出什么、在哪里失败。[官方 Workflow Studio](https://dify.ai/workflows)

新版 Agent Build Mode 的公开方式是通过聊天共同完成任务、纠正结果，将形成的关键指令、技能和工具保存下来。官方将 Agent 与工作流分工为：前者处理任务方法，后者组织时机、前后顺序及异常处理。不能把“聊天构建 Agent”直接扩展成“任意自然语言一键生成完整 DAG”的事实结论。[官方新版 Agent 说明](https://dify.ai/blog/why-we-redesigned-dify-agent)

Human Input 节点提供运行中的暂停与人工反馈。它适合需要审核或选择分支的步骤，但不等于需求定义阶段自动澄清了全部问题，也不适合机械加入所有座舱交互。[官方 Human Input 说明](https://dify.ai/blog/the-human-input-node-bringing-human-judgment-into-automated-workflows)

我们的分析：生日航海的故事、角色与回应可以灵活生成；等待、暂停、奖励、章节推进应由明确程序管理。每次成功执行还需有来源与结果，不能由模型的一句“完成了”代替回执。

## Kiro：将用户意图保存为持续可修改的规格

Requirements-First 先从提示生成需求与验收条件，再形成设计和任务。需求包含触发情境、预期行为及异常，标准流程允许在进入下一阶段前审阅修改。[官方 Requirements-First](https://kiro.dev/docs/specs/feature-specs/requirements-first/)

Analyze Requirements 检查需求间矛盾、歧义、未声明假设和遗漏边界，提出澄清问题；它是一项辅助分析能力，不是需求正确性的形式化证明。[官方需求分析](https://kiro.dev/docs/specs/analyze-requirements/)

Quick Spec 先集中提出澄清问题，再顺序生成需求、设计与任务，不逐阶段设置审批门槛。它说明可保留规格产物，同时降低交互负担。[官方 Quick Spec](https://kiro.dev/docs/specs/quick-spec/)

Steering 用项目文档持续提供产品、技术与结构背景，并支持按范围加载指导资料。OAKEgde Studio 的项目主文档、设计规范和节点契约应实际进入相关 AI 调用的上下文；仅存在文件或飞书中还不够。[官方 Steering](https://kiro.dev/docs/steering/)

我们的分析：把需求保存为独立对象，才能在多轮对话后仍核对目标是否被遗漏。前台可以只显示简短的理解摘要，完整规格由系统维护、按需展开。

## 自然语言生成完整工作流代码是什么意思

以儿童关怀为例，用户表达的是“识别后排儿童危险后，自动在中控展示后排视频”。完整实现还需要读取输入、调用模型、校验返回、判断分支、调用播放接口、等待回执、处理失败和取消。

下列是解释概念的示意，不是任何竞品的内部源码：

```text
接收图片
调用具有图片能力的模型，校验返回结果
风险：打开独立配置的后排视频，等待播放回执
无法判断：说明原因，等待新证据
正常：记录本次未观察到定义中的风险
视频失败：说明画面不可用，不报告已展示
```

开发阶段的 AI 负责生成或修改这些实现。运行阶段，只有确需理解、识别或创作的环节才调用模型；条件、进度与回执处理可以由程序确定执行。

“完整”表示流程有执行实现，不表示摄像头、地图、车控等外部资源自动存在。新的设备适配器仍需真实接口、权限和环境，不能靠生成函数名称获得能力。

## 准确性应该怎样建立和衡量

从公开产品机制中，可以归纳出减少歧义、提供能力上下文、检查结构、实际运行、观察错误和迭代修复这些方向。三家的具体内部算法未公开，以下是适用于 OAKEgde Studio 的工程建议，不声称它们采用完全相同的流水线。

| 验证层 | 应回答的问题 | 需要的证据 |
| --- | --- | --- |
| 需求理解 | 做的是用户真正想要的体验吗 | 原始需求与规格对应、关键歧义处理记录 |
| 结构与契约 | 参数、类型、数据连接、分支是否有效 | schema/连线检查结果和能力版本 |
| 运行行为 | 等待、暂停、失败、取消及动作是否按定义执行 | 实际执行轨迹、状态与回执 |
| 模型任务 | 识别或理解是否正确 | 有标注的数据集、漏报/误报/未知率等任务指标 |
| 体验质量 | 故事是否连续、有趣，互动是否易懂 | 内容评审、完整旅程试用和用户反馈 |
| 环境交付 | 在声明的设备和网络条件下能否运行 | 明确的设备、服务、版本和实测记录 |

重要反例：AI 把“风险时显示后排视频”误解为“显示上传照片”，再编写“检查照片显示”的测试，可能代码和测试都通过，原始目标仍未满足。

因此验收预期应由原始需求独立确定并版本化；修复实现时不能为了通过而随意改写预期。保留固定正常、异常和边界案例，再让 AI 补充额外测试。模型自评或第二个模型审查只能增加检查信号，不能代替真实结果与独立标准。

## OAKEgde Studio 可借鉴的六项做法

以下均为产品建议，尚未因本文自动进入实施。

| 建议 | 借鉴来源 | OAKEgde Studio 的具体落点 | 收益 |
| --- | --- | --- | --- |
| 持久的场景需求规格 | Kiro | 原始目标、必需行为、创作空间、缺口、异常、验收 | 多轮修改不丢失原始目的 |
| 用自然语言修改局部体验 | Coze | 选中节点或子流程后提出修改；显示影响范围 | 减少重做和误改无关部分 |
| 创作与执行分工 | Dify | 内容交给模型，规则/状态/回执交给程序 | 创意变化不破坏确定性行为 |
| 能力库允许扩展 | Coze | 已登记能力直接组合；缺失能力提出扩展，验证后注册 | 不把创新限制成有限场景模板 |
| 生成后验证与有限修复 | Coze / Dify | 候选流程在受控环境运行，对照预期检查，失败保留证据 | 从“生成了一张图”推进到“有运行依据” |
| 按需使用项目知识 | Kiro | 加载相关设计、节点、接口和案例，并记录版本 | 减少重复解释和使用过时约定 |

基础节点契约是可复用能力边界，不应变成创意清单上限。用户画布可展示有业务意义的子流程，必要时展开基础能力和执行详情；这种层级是我们的设计建议，不是当前界面已实现的事实。

## 两个场景如何应用这些经验

### 儿童关怀

用户目标：发现所定义的后排儿童风险后，在 HMI 左上角打开独立后排视频，减少驾驶员回头查看的需要。

需求规格要区分：识别照片与展示视频是两个来源；风险行为的定义；无法判断、视频不可用和用户关闭时的处理；哪些结果需要真实播放回执。没有后续证据时不能认定风险解除。

业务流程可表达为“观察后排 → 判断风险 → 展示后排画面”；内部再展开图片输入、模型调用、字段检查、分支、媒体播放与记录。照片用于模拟触发，不代表持续摄像头监测。

建议验收至少包含：风险能触发；正常不误触发；未知不当作安全；视频失败不报成功；取消后的迟到结果不重新弹窗。视觉判断正确与流程动作正确分别评测。

### 朵朵生日航海

用户目标：去滴水湖的生日旅程具有航海主题、惊喜与可参与的互动。

固定目标与规则：服务对象、旅程背景、暂停/继续/退出方式、到达时的收尾、内容失败时保留进度。允许创作：角色、故事结构、谜题、互动节奏、惊喜形式。缺失的年龄、时长等信息明确为待补或可见假设，不自行写成事实。

业务流程可表达为“启航仪式 → 沿途探索 → 生日惊喜”。并非每一段都必须答题或发奖励；叙事、角色扮演和自由讨论可采用不同组合。

建议验收包括：中途暂停可恢复；同一事件不重复奖励；生成失败不推进；提前到达仍有合理收尾；固定题目答案不被临时改写。趣味、连贯与适龄另做体验评审，驾驶员与乘客的交互对象要明确。

## 建议的实施顺序与取舍

| 顺序 | 交付物 | 如何判断有收益 |
| --- | --- | --- |
| 先补需求追踪 | 把已有场景规格、关键节点和验收案例逐项关联，显示能力缺口 | 能指出每个必需行为由哪里实现、在哪里验证 |
| 再补验证闭环 | 复用现有检查器与执行器，运行候选流程；读取失败，有限修复 | 失败不覆盖有效版本；通过项有执行记录，不仅是模型自评 |
| 再开放新能力实现 | 新能力提案、适配器、契约测试、受控运行、注册与版本 | 新能力可替换、可复用、可解释失败；不会直接越过现有约束 |

不建议把每一步都变成人工审批，也不建议把全部技术参数放到聊天区。右侧保留简洁对话，关键误解需要用户修正，详细规格、依赖和验证证据按需查看。

需要避免的误用：把 Dify 的 Agent 构建当作已证实的全流程生成；把 Kiro 所有模式理解为逐步审批；把 Coze 的自由代码生成理解为能力无需契约；把切换模型视为准确性的充分条件。
